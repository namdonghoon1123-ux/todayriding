# 지침 충돌 검토

첨부된 제품/MVP 요구사항과 디자인 가이드를 기준으로 충돌, 모호점, 권장 해석을 정리한다.

## 결론

치명적인 충돌은 없다.

다만 구현 전에 해석을 고정해야 할 지점은 있다. 아래 권장 해석을 따르면 MVP 작업 순서가 흔들리지 않는다.

## 1. Supabase 메인 저장소 vs 라이딩 중 로컬 우선 저장

상태: 충돌 아님

설명:

- 한 지침은 Supabase를 메인 저장소로 둔다.
- 동시에 GPS 기록은 절대 유실되면 안 되므로 라이딩 중 로컬에 먼저 저장하라고 한다.

권장 해석:

- Supabase는 장기/동기화 저장소다.
- LocalRideStore는 라이딩 중 원장에 가깝게 취급한다.
- 라이딩 종료 후 RideSyncService가 Supabase로 업로드한다.
- 업로드 실패 시 sync_status를 pending으로 둔다.

## 2. SwiftData 또는 SQLite 선택

상태: 미결정 지점

설명:

- 원문은 로컬 임시 저장을 SwiftData 또는 SQLite 중 적합한 방식으로 열어두었다.

권장 해석:

- 지금은 LocalRideStore 프로토콜을 먼저 정의한다.
- MVP에서는 SwiftData를 우선 검토한다.
- GPS 포인트 대량 쓰기, 배치 처리, 마이그레이션 제어가 중요해지면 SQLite로 바꿀 수 있게 둔다.

## 3. 백그라운드/잠금화면 기록 vs 포그라운드 안정화

상태: 범위 모호점

설명:

- 제품 지침은 실제 GPS 기록, 백그라운드 위치, 배터리, 잠금화면 상태 기록을 실기기 테스트 대상으로 언급한다.
- 권한 지침은 1차 MVP에서 백그라운드 위치 권한을 신중하게 다루고 포그라운드 기록부터 안정화하라고 한다.

권장 해석:

- 1차 MVP의 필수 구현은 포그라운드 기록이다.
- 백그라운드/잠금화면 기록은 구조와 TODO를 남기되, 안정화는 2차 단계로 둔다.
- 실기기 테스트 체크리스트에는 포함하되 완료 기준으로 강제하지 않는다.

## 4. 실제 기상청/에어코리아 API vs Mock 우선

상태: 충돌 아님

설명:

- 데이터 지침은 한국 기준 기상청/에어코리아 API를 우선 고려한다.
- 작업 방식은 API 키가 없을 수 있으므로 Mock 서비스부터 만들라고 한다.

권장 해석:

- MVP 구현은 WeatherService, AirQualityService 프로토콜과 Mock 구현이 필수다.
- KMAWeatherService, AirKoreaService는 후속 구현체다.
- API 키 구조만 placeholder로 마련하고 하드코딩하지 않는다.

## 5. 공유 카드와 자동 업로드 제외

상태: 충돌 아님

설명:

- 공유 카드는 1차 MVP에 포함된다.
- 인스타그램 자동 업로드, 블로그 자동 작성/게시, 영상 자동 생성은 제외된다.

권장 해석:

- 앱 내부에서 공유 카드 이미지를 생성한다.
- ShareLink 또는 UIActivityViewController로 사용자가 직접 공유한다.
- 외부 서비스 자동 게시 로직은 만들지 않는다.

## 6. PhotosUI 언급 vs 사진 기능 최소화

상태: 범위 모호점

설명:

- 기술 방향에는 PhotosUI가 언급된다.
- ride_photos 테이블은 필요하면 초안만 만들고, 사진 기능은 1차 MVP에서 최소화해도 된다고 되어 있다.

권장 해석:

- 1차 MVP에서 필수는 공유 카드 이미지 저장/공유다.
- 라이딩 사진 첨부 기능은 필수가 아니다.
- PhotosUI는 사진 첨부를 구현할 때 도입한다.

## 7. 디자인 가이드의 기록 리스트 화면

상태: 범위 확장 후보

설명:

- 디자인 가이드에는 기록 리스트 화면이 포함되어 있다.
- MVP 핵심 흐름은 홈 -> 라이딩 중 -> 요약 -> 공유 카드다.

권장 해석:

- 기록 리스트는 1차 MVP 핵심 흐름의 필수 완료 기준이 아니다.
- 로컬/Supabase 저장 이후 자연스럽게 붙일 1.5차 또는 2차 화면으로 둔다.
- 디자인 토큰은 미리 참고하되, 구현 우선순위에서는 뒤로 보낸다.

## 8. 다크 디자인의 큰 숫자/강한 UI vs 라이딩 중 안전성

상태: 보완 필요

설명:

- 디자인은 큰 숫자와 스포티한 강조를 요구한다.
- 라이딩 중 화면은 조작 최소화와 명확성이 중요하다.

권장 해석:

- RideTrackingView에서는 장식보다 가독성을 우선한다.
- 터치 타깃, 대비, 정보량 제한을 우선하고 브랜드 효과는 CTA/종료 버튼 정도로 제한한다.

## 9. Supabase SDK 도입 시점

상태: 미결정 지점

설명:

- Supabase를 메인 저장소로 사용한다.
- 동시에 외부 의존성을 한 번에 많이 추가하지 말라고 한다.

권장 해석:

- 먼저 SupabaseService 프로토콜과 Mock 또는 Noop 구현을 만든다.
- Swift Package Manager로 Supabase Swift SDK를 붙이는 것은 프로젝트가 컴파일되고 핵심 흐름이 연결된 뒤 진행한다.

## 파일별 재검토

### 00-index.md

상태: 충돌 없음

확인 내용:

- 각 문서의 역할을 안내하는 인덱스 문서다.
- "지금은 앱 코드 구현 전 단계"라는 문장은 현재 문서화 작업 기준으로 맞다.
- 이후 앱 코드 구현이 시작되면 이 문장은 "초기 지침 작성 단계의 기준"으로 바꾸는 것이 좋다.

권장 조치:

- 지금은 수정 불필요.
- 코드 구현 단계로 넘어가면 상태 문구만 갱신한다.

### 01-product-brief.md

상태: 모호점 있음

확인 내용:

- "백그라운드 위치, 배터리, 잠금화면 상태 기록은 iPhone 실기기 테스트"라고 한다.
- 03-data-api-storage.md는 "백그라운드 위치 권한은 신중하게, 우선 포그라운드 기록부터 안정화"라고 한다.

판정:

- 직접 충돌은 아니다.
- 01은 장기 테스트 대상, 03은 MVP 구현 우선순위를 말하는 것으로 해석한다.

권장 조치:

- 1차 MVP 완료 기준에는 포그라운드 기록만 둔다.
- 백그라운드/잠금화면 기록은 TODO와 실기기 테스트 항목으로만 둔다.

### 02-mvp-scope.md

상태: 작은 범위 모호점 있음

확인 내용:

- 종료 후 화면에는 "최고 속도"가 포함된다.
- 공유 카드에는 "평균 속도"만 필수로 적혀 있다.
- 06-visual-design-guide.md의 공유 카드 레이아웃에는 "시간/평균/최고 3등분"이 있다.

판정:

- 공유 카드 필수 정보에서 최고 속도 포함 여부가 다르다.

권장 조치:

- MVP 필수 공유 카드 정보는 02를 따른다.
- 최고 속도는 디자인 여유가 있으면 표시하되, 공유 카드 MVP 필수 조건으로 강제하지 않는다.

### 03-data-api-storage.md

상태: 모호점 있음

확인 내용:

- Supabase를 메인 저장소로 둔다.
- 동시에 라이딩 중 위치 포인트는 로컬에 먼저 저장한다.
- ride_photos 테이블 초안이 있지만 사진 기능은 최소화한다고 한다.

판정:

- Supabase와 로컬 저장은 충돌이 아니라 저장 계층의 역할 분리다.
- ride_photos는 1차 MVP 필수 기능으로 오해될 수 있다.

권장 조치:

- Supabase는 장기 저장/동기화 대상, LocalRideStore는 라이딩 중 유실 방지 저장소로 정의한다.
- ride_photos는 스키마 후보로만 유지하고 실제 사진 첨부 기능은 MVP 밖으로 둔다.

### 06-visual-design-guide.md

상태: 범위 확장 후보 있음

확인 내용:

- 기록 리스트 화면이 포함되어 있다.
- 시간대별 적합도 카드가 홈 레이아웃에 포함되어 있다.
- 공유 카드에는 최고 속도 표시가 포함되어 있다.
- MVP 핵심 완료 기준인 02에는 기록 리스트가 없다.

판정:

- 디자인 문서가 MVP 필수 범위보다 넓다.
- 기록 리스트는 명확히 1차 MVP 필수 흐름 밖이다.
- 시간대별 적합도는 홈 UX를 풍부하게 하지만, 실제 시간대별 예보 계산이 없으면 Mock/간단 계산으로 시작해야 한다.

권장 조치:

- HomeView, RideTrackingView, RideSummaryView, ShareCardView 디자인에는 우선 적용한다.
- 기록 리스트는 후속 범위로 둔다.
- 시간대별 적합도는 Mock 데이터 또는 단순 계산으로 표시하고, 실제 예보 연동은 후속으로 둔다.

### 07-implementation-plan.md

상태: 충돌 없음

확인 내용:

- Mock 서비스 -> 점수 계산 -> HomeView -> Location/RideTracker -> 저장/동기화 -> 공유 카드 순서다.
- 01, 02, 03, 04의 우선순위와 일치한다.

주의점:

- 10단계 로컬 임시 저장이 RideTrackingView 뒤에 있어, 초기 화면 구현 중에는 메모리 기반 기록으로 시작할 수 있다.
- 데이터 유실 방지까지 검증하려면 10단계 이후에 RideTrackingView와 RideTracker를 다시 연결 점검해야 한다.

권장 조치:

- 현재 순서를 유지한다.
- 10단계 완료 후 기록 흐름 회귀 테스트를 한 번 더 한다.

상태: 자기모순 없음

확인 내용:

- MVP 필수 범위와 후속 범위를 나누는 기준이 02-mvp-scope.md와 일치한다.

권장 조치:

- 구현 중 새 결정이 생기면 이 문서에 추가한다.

## 최종 권장 작업 기준

1. Mock 기반 앱 흐름을 먼저 완성한다.
2. 로컬 저장은 데이터 유실 방지 책임을 가진다.
3. Supabase는 동기화 대상이며 초기에는 인터페이스/스키마 초안으로 충분하다.
4. 백그라운드 위치, 실제 API, 사진 첨부, 기록 리스트는 MVP 이후로 밀어도 된다.
5. 디자인 가이드는 HomeView, RideTrackingView, RideSummaryView, ShareCardView에 우선 적용한다.
